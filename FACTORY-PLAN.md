# An autonomous software factory, one outcome first

The first demonstration should answer two questions. Can the factory deliver a real change that an independent reviewer can verify after a worker fails? Can it then use evidence from that delivery to propose a correction and support a decision about using it again?

Keep Pstack and your changes to it in a Git repository you own. The factory pins the skills it uses and selects them for each bot in `agents.toml`. For the pilot, a Temporal delivery worker runs the Pstack-guided Codex CLI through the operator’s existing ChatGPT subscription. Harbor starts fresh instances of this same workflow for evaluation.

Build the verifier first. Put one submission through Temporal, then replace the scripted contributor with one engineering agent. Carry the resulting product change through review. Only then use Harbor to compare two versions of the factory on fresh work. A reviewer can conclude **hold** or **reject** and the demonstration still succeeds. A claim that the factory improved needs stronger evidence.

## One bot configuration

`agents.toml` in the repository root is the only file operators edit to define bots. This proposed pilot profile is read by the factory. Resolve its named skill references against the factory’s `config/skills.lock`, bind only the named tools allowed by delivery policy, and reject unknown fields, runtime names and unsupported permissions before dispatch.

```toml
[factory]
schema_version = 1

[factory.bots.delivery-engineer]
on_event = "outcome.approved"
workflow = "deliver-outcome"
runtime_profile = "codex-cli-chatgpt"
instructions = "Write a failing behavioral test. Submit the exact commit and its test evidence."
skills = ["pstack/how", "pstack/tdd"]
tools = ["workspace.read", "workspace.edit", "workspace.test", "submission.create"]
timeout_minutes = 30
max_attempts = 2
```

If the optional Harness runtime is enabled later, add native `[[agents]]` registrations in this same file for workflow type, queue and startup schema. The factory owns `[factory.bots.*]`, including triggers, instructions, skills, tools, runtime and limits. Referenced skill files contain the methods. Dependency locks and generated run manifests capture resolved versions. Keep account credentials in the trusted runner’s credential store. [Native registry format][registry]

**At run start**, resolve the selected bot once. Archive its digest and source revision, CLI build, selected model and reasoning settings, exact skill digests and effective tool permissions. Record the execution environment and worker build separately. Reuse this snapshot after an interruption. A reviewed profile change applies to new runs.

## Where skill changes live

| What changes | Where the reviewed change lives | How a bot receives it |
|---|---|---|
| A Pstack skill, playbook or shared helper | Your Pstack Git repo. Bring later mirror updates in as reviewable changes with their upstream revision. | The factory updates the `pstack` source pin in `config/skills.lock`. |
| A new skill you author | The same repo under a distinct name such as `team/release-check`, or a product repo if its maintainers own the procedure. | Add its source and path to the lock. Select it by name in `agents.toml` for the bots that need it. |
| A skill maintained elsewhere | Pin the maintainer's published commit. Carry a local change in an owned fork, or propose it upstream and pin the accepted revision. | The lock identifies the chosen source. Its qualified skill name can stay the same across a fork. |
| A bot selects the wrong skill | The factory's `agents.toml`. | Evaluate the selection change with skill contents pinned. A loader defect belongs in the factory code. |

The lock maps each qualified skill ID to its repository, full Git commit, path and digest of the files it uses, including referenced playbooks and helpers. Resolve only the selected versions into the run workspace. Treat the existing `.agents/` tree as an import input. Verify that a stale local installation cannot shadow a locked skill. A run records the effective digests so a change to a helper shared by several skills is visible.

## Ownership and authority

**Inner loop.** The factory accepts a versioned outcome and resolves its configuration once. The agent investigates, designs, writes a failing test, implements, and refactors. A separate verifier checks the exact submitted revision. Temporal reconciles the PR, CI and review against that revision, waits for the required authority, then records merge, deployment and observed results where applicable. A passing test grants no external permission.

**Outer loop, or autoloop.** Read closed and interrupted runs, score them, group failures, and propose a specific diff and a falsifiable prediction. The factory may generate proposals and schedule experiments within a pre-authorized evaluation budget. The candidate is a disposable evaluation input. The skill maintainer reviews the source change. Factory reviewers separately decide whether to adopt that revision and activate it for eligible runs. Product maintainers approve product actions. Factory reviewers approve configuration changes and promotions.

**Pstack supplies methods.** Use `how` and `why` for investigation, `architect` for design, and `arena` when a choice warrants competing implementations. `create-verification-skill` describes how to launch, diagnose, drive, collect evidence and clean up. Require reviewers using `interrogate` to reproduce findings. `show-me-your-work` can contribute decision records. Instrument tool calls and lifecycle events separately. `reflect` consumes the current transcript and waits for approval to edit. Supply archived runs through a read-only adapter. Prefer `correct`'s order of architecture, types, executable checks, behavioral tests and then documentation. Use the eval and hillclimb methods to freeze criteria and change one variable. Put the operator's stricter TDD rule in the effective configuration and verify the red and green commands in the trace. [Verification method](.agents/skills/create-verification-skill/SKILL.md) · [Reflection](.agents/skills/reflect/SKILL.md) · [Correction](.agents/skills/correct/SKILL.md) · [Evaluation](.agents/skills/poteto-mode/playbooks/eval.md)

**The factory owns the policy.** Keep product source, factory configuration and grader inputs under separately scoped write permissions. A reviewer binds an approval to the actor, action, repository/environment, exact revision or image digest, and expiry. Check those fields at execution. A new head invalidates the previous verification and approval. For an integration merge or squash, verify the resulting tree or merge-queue revision before release. Bound agent tools by execution mode. Give evaluation runs fixture PR, CI and deployment services, with no production credentials or routes.

For the first comparison, vary one proposed skill change or one tool mapping. Check the effective file differences across all skills used by the bot, including shared helpers. The experiment supervisor supplies the same grader, protected tests, policy and benchmark digests to both arms and rejects any mismatch before launch. The Harbor bridge and collector come from the trusted execution image. A future experiment on workflow code runs the candidate in a separate evaluation worker build. Record that build as the treatment and replay saved histories to check upgrade compatibility before activation.

**Defer** a generic workflow language, a second trial scheduler, a dashboard, a fleet of engineering agents, a judge-only quality score and production deployment automation. Start with a single trusted development host and controlled target repositories. Multi-tenant execution and unattended releases need their own design.

## Evidence and recovery

1. **Archive at the point of action.** Write native events, tool requests/results, skill resolution and read events, red/green/refactor evidence, decision records, immutable Git objects, verifier output, CI/review receipts, human corrections and post-release observations. For usage record known values, source and currency or an explicit unknown. Save originals with restricted access and agreed retention. Strip credentials before persistence and create redacted research exports. Normalize trajectories to ATIF alongside native events. [ATIF export][atif]
2. **Make completion checkable.** Store blobs by digest and publish the run manifest last. Record expected artifact kinds, byte sizes, digests, producer and collection status. Reopen every required item and cross-check the verified SHA, grade and reviewer decision. A missing file, wrong SHA or broken event sequence makes the evidence incomplete even if the agent exited successfully. Record failed, cancelled and abandoned attempts with whatever evidence survived. A lease-expiry reconciler records suspected abandonment and checks external state before closing it.
3. **Recover work separately from the workflow.** Checkpoint the base commit, reachable Git bundle, working changes including required untracked test files, environment digest and last completed step after red, green and submission. Restore into a fresh checkout and verify its tree before continuing. If a checkpoint is missing, roll back to the last verified checkpoint and record lost work. If none exists, close the attempt as interrupted and apply the retry budget. Temporal replay must never count as an evaluation trial. [Temporal recovery][temporal-wf]
4. **Reconcile writes.** Persist the intent, canonical request digest and stable operation ID before a push, PR, deploy or Harbor submission. On timeout, inspect the remote by expected ref/head, PR head/base and run marker, deployment key, or Harbor key. Attach a matching receipt. Stop on a conflicting result or an ambiguous provider operation that cannot be looked up. Compare-and-swap mutable pointers and branch refs. Deduplicate evidence by source event identity. A retried non-idempotent tool command also needs a receipt or a restore to a known workspace state.
5. **Capture the CLI stream while live.** A trusted worker attaches its collector before launching `codex exec --json`, archives redacted JSONL and exit status, and records usage where reported. Identify each child process by attempt. On worker loss, reconcile or fence the prior process before resuming from a verified checkpoint. Record gaps explicitly. If the optional Harness is evaluated later, probe its independent stream retention and resume behavior. [CLI events][codex-exec] · [Harness stream limits][stream] · [Harness resume semantics][agent-client]

## How Harbor should run the real factory

1. The experiment workflow reserves the full bounded batch, including verification, infrastructure and retries. A short activity submits a locked job through the Harbor client with a caller-supplied idempotency key per experiment arm/batch. A duplicate returns HTTP 409 with the original ID. Reconcile that ID and the saved request digest, then monitor by durable timers and short status reads. Persist every rollout and retry. Client disconnect does not cancel a job. [Server API at the pin][server] · [Duplicate-key implementation][idempotency]
2. Install `FactoryAgent` in the Harbor execution image. Pass a supported server-side task path or pinned Git source and a locked factory digest. A custom `BaseAgent` gets `setup(environment)` and `run(instruction, environment, context)`. The server gives its trial the rollout UUID, which becomes the agent's `context_id`. Use it for a stable evaluation delivery workflow ID. A retry gets a new rollout UUID. Discovery lists built-ins, while job execution preflights the configured agent. Test custom import through a real server submission. The pinned server rejects custom job metrics, source jobs and workspace streaming. Keep comparisons and trace export in the factory. [External agent interface][agent-base] · [Server resolution][resolution] · [Rollout execution][executor]
3. `FactoryAgent` starts a fresh `deliver-outcome` Temporal workflow for the rollout with the resolved bot digest. Both product and evaluation workers run the same workflow build, pinned Pstack methods and `codex-cli-chatgpt` adapter. Only the workspace, verifier and external-service bindings change. Keep Harbor’s live `BaseEnvironment` in its owning process and route the trial’s file, shell and application operations through a revocable trial-scoped binding. The trusted Codex process holds the login. Test that all its tool paths, including built-in commands, stay inside the assigned workspace. The built-in Harbor Codex agent can test the CLI alone, and its auth-file mode copies credentials into the environment. Use the factory bridge for end-to-end trials and keep the subscription credential out of the trial and grader. [Pinned Harbor Codex integration][harbor-codex]
4. At submission, the delivery workflow parks awaiting a verification receipt. The adapter exports the immutable bundle, patch, native events, `trajectory.json`, partial manifest and the usage it recorded in `AgentContext`. It stops the trial’s tool binding, releases the lease and returns. **This return allows Harbor to start grading.** Harbor collects outputs, stops the agent environment and runs the protected verifier on the submitted commit. Specify required output digests and disregard unrelated files, including files in Harbor's automatic artifact directory. [Trial execution order][trial-order] · [Separate verifier example][separate] · [Artifact transfer][transfer]
5. A supervisor outside the adapter reads the rollout result and delivers a deduplicated receipt bound to the rollout UUID, submitted SHA and grader digest. The parked workflow either closes with a failed check or continues through fixture PR, CI, review and release using the archived commit. Those steps can run after the sandbox is gone. Close the factory manifest only after the fixture receipts arrive. Score both the grade and the requested delivery behavior. If another edit is needed, preserve the rejected attempt and allocate a fresh, budgeted trial. Test a lost grade notification by reconciling from the persisted rollout result.
6. Propagate cancellation both ways. The supervisor requests Harbor cancellation, the adapter revokes its lease and cancels the evaluation workflow, and a reconciler confirms both terminal states and sandbox cleanup. A server crash can leave provider resources behind. The pinned server records interrupted running attempts and pauses queued work on recovery in this case. Inspect the provider, fence the old attempt, persist its costs and recoverable evidence, then permit a bounded fresh Harbor attempt. Harbor owns the sandbox lifetime. [Harbor recovery][service]

## Comparing factories and deciding what to promote

**Diagnose before editing.** Record which skill was required, present, resolved, included in the model context, and followed by an observable action. Classify a missing skill, a load failure, a loaded instruction that was skipped, or an incorrect instruction separately. Preserve tool or environment errors and ambiguous outcome specifications as other possible causes. A file read alone cannot establish why an agent acted. Compare with a successful run or small reproduction. Retain `unknown` if the evidence cannot separate explanations.

**Test the skill where it runs.** For a delivery skill such as `pstack/tdd`, start fresh paired Harbor trials through `FactoryAgent` and the same Temporal delivery workflow. Give one arm the active lock and the other a candidate lock. Keep the bot selection, Codex runtime, tasks, budgets and grader fixed. If changing a shared helper affects another selected skill, include a regression case that exercises that skill.

For an outer-loop skill such as `pstack/reflect`, run both versions of the proposal step against the same archived traces, including successes and ambiguous failures. Hide human labels and later corrections from both arms. An independent reviewer scores whether the diagnosis cites the right evidence, the proposed fix targets the cause and the skill abstains when evidence is insufficient. When a proposal claims better delivery, test that proposed fix separately on fresh held-out Harbor tasks. Keep the scoring criteria and promotion authority outside the candidate's control.

**Freeze the task and the judge.** Start with the original contract and pre-solution repository. Pin environment, service fixtures, acceptance and regression checks, output contract, task class, difficulty and provenance. Exclude the solution, future history, corrections and hidden grading material from the agent's inputs. A known solution must pass, the unchanged base must fail the intended check, and a deliberately defective submission must fail a regression. Freeze the grader before either arm runs. Put related tasks in the same split to prevent leakage. Grader changes get independent review and a new version. Regrading historical outputs tests a verifier change. A change to skills, model, tools or workflow requires new trials. [Harbor task example][separate] · [Regrade semantics][regrade]

**Start with an affordable comparison.** A proposed demonstration uses one historical tuning task, two distinct held-out tasks of known class and difficulty, and three fresh paired repetitions per task. That is 18 assigned runs before retries. The historical task can explain the change. Only the held-out results inform promotion. Freeze model settings except the variable under test, images, fixtures, timeouts, retry policy, task order randomization and paired seeds where supported. Bound trial count, concurrency, elapsed time, retries and infrastructure spend before dispatch. Record reported tokens and account-limit events. If subscription quota is exhausted, checkpoint and wait within the deadline, or mark the assignment incomplete. The pilot never switches automatically to API billing. Record per-run subscription cost as unknown unless attributable. A future API comparison needs its own approved spend cap.

**Decide in order.** First require complete required evidence, valid independent grades and passing mandatory regressions on the exact submission. Report accepted assignments over all planned assignments and scored coverage separately. Then compare acceptance and repeat failures by class and difficulty. Compare time, human effort and cost only after quality gates pass. Before running, specify the minimum useful change, permitted regression margin, uncertainty rule and deployment scope. For a broader promotion, use enough independent held-out tasks for the predeclared paired interval to clear the quality margin. Repeats on one task cannot establish generality. An underpowered demonstration yields a reviewable hold. An optional qualitative judge must be blinded to the arm and calibrated against executable results and independently labeled examples.

**Account for the denominator.** Harbor's server summarizes valid rewards from the latest attempt and reports their coverage. That mean can hide an unsuccessful assignment. Keep every attempt, failure, cancellation, invalid grade, storage error, retry and infrastructure charge in the factory report. Record accepted outcomes, regressions/reopens/rollbacks within a stated window, request-to-accept cycle time, active reviewer minutes, repeated causes and total experiment spend. Cost per accepted outcome includes all attributable attempts and infrastructure divided by accepted outcomes. With zero accepts it is undefined. With incomplete billing, show known subtotal and coverage. Keep evaluation spend separate from product delivery spend. [Server result model][summary]

## Failure drills and the decisions they settle

| Inject this failure or uncertainty | Smallest experiment | Required observation and next action |
|---|---|---|
| Worker dies after an effect, including a push or deploy | Drop the acknowledgement, discard the workspace, restart and inspect actual remote or fixture state | One matching receipt, restored tree, zero duplicate effects. If the provider cannot establish the result, record an ambiguous action for review. |
| Repeat or change a Harbor submission | Drop the first HTTP response, then resubmit the same key. Try a changed payload against the factory ledger. | Reattach to the original job via 409. Reject a changed request under the same key before submission. |
| Cancellation races with a tool or upload | Cancel one queued rollout and one active rollout. Disconnect the adapter once during cleanup. | Stop granting work, fence the lease, reconcile both systems, preserve partial evidence and charges. No orphan after the configured cleanup deadline. |
| A sandbox or Harbor server disappears | Remove one trial container mid-edit. Separately stop the server mid-run. | Record failed/interrupted attempt and provider inventory. Retry in a fresh Harbor trial only after cleanup and budget reconciliation. Restore a production workspace only from a verified checkpoint. |
| Grading or evidence looks successful despite missing data | Suppress bundle collection, corrupt a digest, omit the reward or cost, then try to promote. | Missing proof blocks acceptance. Missing cost blocks a cost claim. Preserve coverage and known spend in either case. |
| Runtime or credential boundary mismatch | In delivery and a Harbor trial, issue the same workspace operation and compare the recorded runtime pins, where the operation ran and which files it could reach. Interrupt a CLI run, exhaust a test quota and lose a grade notification. | Require isolated tools, no readable account secret, no duplicate CLI process, no automatic API billing and one reconciled grade for the submitted commit. If isolation fails, keep full-factory trials blocked until the binding is corrected. |
| Pstack instructions present but ineffective | Compare the files loaded by the runner with the lock for the operator-owned Pstack commit. Dispatch one outcome and inspect resolved bytes, tool calls, TDD order and the skill-read trace. | Accept the bundle only if the required actions occur. Record any required tool mapping in the reviewed factory configuration. |
| Apparent improvement disappears across tasks | Repeat baseline against itself first on the tuning set. Run the frozen paired design on held-out tasks under the agreed cap. | Estimate ordinary variation before interpreting the candidate. Hold when the quality margin or uncertainty rule is unmet. Never tune on promotion results and reuse them as fresh evidence. |

The implementation inputs still needed are a real target outcome and reviewer, authorized effects, an available subscription allowance and a bounded infrastructure budget, and an appropriate observation window. None is needed to start PR 01. The integration that most threatens the demonstration is the lifetime of Harbor's environment handle across worker loss. PR 07 must prove that a dead handle cannot keep issuing tools or turn a partial submission into an accepted one.
